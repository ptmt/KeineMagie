# ChatGPT authorize request diagnosis

## Confirmed protocol defect

`server/provider.go` previously generated `ext_agent_host_id` as `urn:uuid:` plus a 43-character base64url random token. This is not a UUID URI. A disposable request generated by the actual `/v1/provider/connect` → `/v1/provider/bootstrap/start` handlers emitted:

```
https://auth.openai.com/api/accounts/authorize
agent_name_hint=KeineMagie
client_id=dynamic_agent_client
ext_agent_host_id=urn:uuid:YRSGlvhmTQlB6_BqlEmYqCF3TOn8P4sUVrzxop9t-OQ
redirect_uri=http://127.0.0.1:49514/auth/callback
response_type=code
resource=https://api.openai.com/v1
scope=openid profile email offline_access resource.invoke chatgpt.tokens.use.direct
code_challenge_method=S256
code_challenge=<fresh disposable S256 challenge>
state=<fresh disposable state>
nonce=<fresh disposable nonce>
```

No real owner session, saved provider credentials, token hints, code exchange, or consent was used. The disposable test started an IPv4 loopback listener before generating the URL.

## Current official reference

Direct HTTPS fetches returned HTTP 200 with full Markdown from:

- https://developers.openai.com/siwc/token-sharing-open-source.md
- https://developers.openai.com/siwc/token-sharing-open-source/sign-in.md
- https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms.md
- https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery.md

The overview explicitly requires UUIDv4's hyphenated string after `urn:uuid:` for UUID host IDs; it also supports RFC 9278 thumbprint URIs and `did:key`. The sign-in page documents exactly the endpoint, client ID, scope, resource, and callback path already emitted by this application. There is no evidence here that the documentation is fabricated or unpublished. The first extraction helper truncated the table; direct retrieval returned the complete 16,303-character sign-in document.

The VM guide describes local OAuth followed by secure credential transfer. It does not validate the iOS-to-remote-server PKCE bridge topology. That remains a separate acceptance/compliance question.

## Fix and tests

New host IDs are real UUIDv4 URIs. Existing malformed host files matching the exact legacy 32-byte base64url shape are replaced atomically under the existing host lock. Valid existing hosts are preserved. UUIDs remain stable on restart; host files remain owner-only. Neither authorize endpoint nor native allowlist needs changing.

RED: `go test -run 'TestProviderAuthorizeUsesDocumentedUUIDHost|TestProviderMigratesOnlyLegacyMalformedUUIDHost' -v .` failed on invalid emitted host and missing migration.

GREEN: those tests pass; `go test ./...`, `go test -race ./...`, and native/Core `swift test` (41 tests) pass.

`TestProviderAuthorizeDiagnostic` is an opt-in disposable harness. Set `KEINEMAGIE_AUTHORIZE_PROBE` to an owner-only scratch output path; optionally set `KEINEMAGIE_AUTHORIZE_PROBE_WAIT=1` to keep its loopback listener alive for 180 seconds while viewing the public provider page. It saves only the generated authorization URL, never app session or provider credentials.

## Real network result and explicit limits

Both original and fixed requests were navigated in a fresh dedicated browser session. Both remained on Cloudflare's `Performing security verification` page, not the provider authorization UI. Original browser Ray ID: `a584d1edea03064e`; fixed browser Ray ID: `a584da1ddc9fdbc9`.

A direct HTTP request for the fixed URL returned **HTTP 403**, `Server: cloudflare`, `CF-Ray: a584db3e3e0bdc6c-FRA`, HTML title `Just a moment...`.

The fixed handler-generated host was `urn:uuid:f3e8d46b-689f-4552-8df9-93a31fa0fee6`. No provider controls were bypassed. The native desktop capture alternative was unavailable (cua-driver session setup failure); a Safari AppleEvent read timed out.

**The user's `invalid authorize_request` could not be reproduced behind this security interstitial, and no precise upstream OAuth error_description was obtained. The malformed UUID is a proven protocol defect, not yet a network-proven complete explanation of that specific provider error. Authorization-page acceptance and completed authentication remain unverified.**

No deployment, commit, push, or real-user account mutation was performed.
